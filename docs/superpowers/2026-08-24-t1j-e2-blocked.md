## Blocker B — no GUI-free route reaches a searching `computeMove()`

**This was found by static reading before Blocker A surfaced, and it survives a JDK being
installed.** It is the more consequential of the two.

E1 established that `FindMove.computeMove()` is itself GUI-free and that `Match()`'s constructor is
GUI-free. What E1 did not trace is how a driver gets a *position* into that `Match`. Tracing it
now closes the gap the wrong way.

**1. The opening book short-circuits the search.** `computeMove()` calls
`InitialMoves.initialMove(match, player)` first and returns its result without searching whenever
that is non-null. **`moveNr > 5` guarantees the opening book is bypassed** — no branch is taken and
the method returns null — so **setting `moveNr ≥ 6` is a sufficient way to force the search path.**

> **Corrected in review round 1.** This first said `initialMove` returns null "only when
> `moveNr > 5`". That overstated it: the final expression
> `return (retMove != null && retMove.getX() >= 0) ? retMove : null;` can also yield null at plies
> 0–5, when the chosen branch produces no move or one with `x < 0`. Sufficiency is all the argument
> needs; exclusivity was never established and is not claimed.

**2. At `moveNr == 0` it throws.** That branch calls `firstMove()`, which dereferences
`match.getMatchData().mdPieRule` — and `Match()`'s constructor sets `matchData = null`. The only
methods that set `matchData` are `prepareNewMatch()` and `updateMatchData()`, and **both call
`RightPanel.getInstance()`**.

**3. `moveNr` cannot be advanced without a GUI class.** It is `private`, and incremented in exactly
two places:

| site | reachable? |
|---|---|
| `setlastMove()` | calls `appendLastMoveList()` → `getMoveString()` → **`GuiBoard.getHoleName()`** |
| `redoSingleMove()` | needs a populated `moves` list |

and `moves` is mutated in exactly two places — `moves.clear()` inside `prepareNewMatch()` (→
`RightPanel`) and `moves.add()` inside `setlastMove()` (→ `GuiBoard`). Both roads lead to a class
the authorization forbids loading.

**4. Same-package access does not help, and neither does subclassing.** Every relevant `Match`
field — `boardY`, `boardX`, `boardDisplay`, `matchData`, `nextPlayer`, `moves`, `moveNr`,
`highestMoveNr` — is declared `private`, so a probe in `net.schwagereit.t1j` cannot set them.

Field privacy alone would **not** close the route: a same-package **subclass** could override
`getMoveNr()` to return 6 and bypass the opening book without touching a private field. That is
shut only by the class declaration itself —

```java
public final class Match extends Observable implements Runnable   // Match.java:24
```

`Board`, `FindMove` and `InitialMoves` are likewise `public final class`; `GeneralSettings` is not
final, but its constructor is private and its sole instance is an eagerly-created `static final`
field, so it cannot be subclassed into use either. **No subclass route exists anywhere on the
engine path.** Declarations are quoted in `02_post_run_correction.txt` §C.

**Therefore reaching a search-exercising `computeMove()` requires either reflection into private
state, or loading a GUI class.** The authorization forbids the GUI class and does not contemplate
reflection. Choosing reflection unilaterally would change what E2 demonstrates — a headless path
that depends on private internals is a materially different claim from one that uses the published
API — so E2 stops rather than picking between them.

### A determinism fact found on the way

`InitialMoves.firstMove()` selects from a seven-entry opening table with an **unseeded
`new Random()`**. The opening-book branch is therefore **nondeterministic by construction**. That
matters for E3 regardless of how the path question is resolved.

## What this does and does not say about T1j

- It does **not** show T1j is unusable as an anchor. It shows the **published API alone** cannot
  drive a search headlessly.
- E1's finding stands and is sharpened: the headless path is narrow, and the narrowness is now
  located precisely — not in `computeMove()`, which is clean, but in **getting a position into
  `Match` at all**.
- E1 marked criterion 7 `~` and recorded that only running it could settle the matter. That caution
  was right, and the static trace has now converted "unverified" into "**blocked on the published
  API**".

## Options, for the reviewer — none of them acted on

1. **Authorize a JDK** into isolated scratch, and **authorize reflection** into `Match`'s private
   state for the probe. Smallest version: set `moveNr` alone; the boards can be configured through
   `Board`'s own API, which is GUI-free. This makes E2 runnable but changes the claim to "drivable
   via reflection".
2. **Authorize a JDK and accept a non-searching probe.** Not viable as-is: `moveNr == 0` NPEs on
   the null `matchData`, so even the opening-book branch cannot run without reflection.
3. **Reconsider the candidate.** If driving T1j requires reflection into private internals, that is
   a real cost to weigh against E0's runner-up, and against the standing question of whether an
   uncalibrated anchor is worth the ladder at all.

**Nothing above is a recommendation to proceed.** E2 is stopped and preserved as required.
