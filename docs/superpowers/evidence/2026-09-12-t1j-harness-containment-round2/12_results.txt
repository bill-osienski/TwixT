THE FOUR, EACH WITH THE SCOPE OF ITS CHECK
------------------------------------------
1. A FAILED BASELINE NOW ABORTS BEFORE THE FIRST INJECTION, AND EVERY REPORTED
   PROBLEM EXITS NONZERO.  Run 1 of the old harness printed `clean baseline: FAIL`
   and `538/538 defects rejected` and returned 0 (preserved as `08_harness_run_
   FAILED_BASELINE.txt` in the round-1 directory). Checked by running the driver
   as a FRESH SUBPROCESS against a throwaway git repository, because an exit status
   cannot be qualified from inside the process that sets it. Scope: the driver's
   own control flow on synthetic controls; it says nothing about the 539.

2. ONLY THE INTENDED FAILURE, FOR ITS STATED REASON, IS A PASS.  `rejected =
   r.returncode != 0` is gone. A control is REJECTED only when the NAMED node
   FAILS -- not errors, not "no tests ran", not interrupted -- and the traceback
   carries the reason the control declares. Everything else is INDETERMINATE, a
   third outcome, never folded into the pass count. Scope: this binds what the
   harness REPORTS; it does not re-aim any control.

3. THE SHARED WORKING TREE IS NO LONGER MUTATED.  Injections happen in a
   `git worktree` made for the run and removed after it. The narrow test checks
   this BY MTIME, not by content -- the old harness also ended with the right bytes
   on disk, because it wrote the defect and wrote the original back. Where a file
   is still restored in place, inside the checkout, the driver first verifies it
   holds exactly what IT injected and STOPS rather than overwrite, preserving the
   checkout; that overwrite is how incident 2 wiped a guard added mid-run. The
   pytest subprocess is held explicitly and a signal stops it -- checked by the
   CHILD'S PID, not by how fast the parent exits, because a parent that merely
   unwinds ORPHANS its child. Scope: a clean tree is REFUSED-if-dirty, stated in
   the code; uncommitted work is not carried into the checkout.

4. READING THE CONTROL LIST CANNOT START A RUN.  `if __name__ != "__main__"` does
   not fire in a namespace where __name__ is ALREADY "__main__", which is what
   `exec(path.read_text())` gives you and how incident 2 started. There is now no
   driver in the control list at all -- checked behaviourally by execing it as
   __main__ and by AST -- and the driver refuses without `--run`.

TWO DEFECTS I INTRODUCED AND THEN FOUND, BOTH PRESERVED
-------------------------------------------------------
* RECORDING RUN 1 HARVESTED 31 REASONS OUT OF 539 (07). Not the controls' fault:
  pytest FITS its `FAILED <node> - <reason>` summary line to the terminal, 80
  columns when stdout is a pipe, and does it two ways -- a short node id keeps a
  TRUNCATED reason, a node id already too long gets NO reason appended at all.
  This programme's test names are nearly all the second kind. The 31 it did get
  were stubs ("Failed..."). The reason now comes from the traceback's `E   `
  lines, which are fitted to nothing. A COLUMNS=200 fix was tried FIRST and
  REMOVED, because its negative control did not catch -- which is the evidence
  that it was not the mechanism.
* THE FIRST MEASURED RUN REPORTED 16 INDETERMINATE (09), and TEN had nothing
  wrong with them: the frozen reasons carried content that differs every run --
  pytest's numbered tmp session (7), object repr addresses (3) and the driver's
  own randomly named checkout (1). A reason that cannot match twice is not a
  check. `stable()` now normalises those three on BOTH sides and at recording
  time; the test records on one run and requires the value to hold on the NEXT.

SCOPE OF EXPECTED_REASONS. The 539 reasons were RECORDED from runs of the driver
and frozen, not authored from the tests. They therefore detect DRIFT -- a control
that begins failing at a different assertion than the one it was observed to
reach -- and they do NOT independently prove that the assertion reached is the
right one. Six of them are ERROR text, marked where they stand.
