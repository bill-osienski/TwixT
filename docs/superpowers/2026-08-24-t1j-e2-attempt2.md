## Failure 1 — `GuiMainWindow` loads when `Match` links

The class-load log, with timestamps:

```
[0.030s] net.schwagereit.t1j.GeneralSettings
[0.060s] net.schwagereit.t1j.Match
[0.061s] java.awt.Component
[0.061s] javax.swing.WindowConstants
[0.061s] javax.swing.RootPaneContainer
[0.061s] java.awt.Container
[0.061s] java.awt.Window
[0.061s] java.awt.Frame
[0.061s] javax.swing.JFrame
[0.061s] net.schwagereit.t1j.GuiMainWindow     <-- forbidden class, loaded
[0.062s] net.schwagereit.t1j.Board
```

**E1's most load-bearing inference was half right, and the wrong half mattered.** E1 predicted that
`GeneralSettings.correct()`'s reference to `GuiMainWindow.SCHEME_NUMBER` would be inlined as a
compile-time constant and would *not* load the GUI class. **That prediction is confirmed** —
`GeneralSettings` loaded at 0.030 s and pulled nothing. E1 then treated that as the residual risk
for headlessness. It was not the risk.

The GUI class arrives through **`Match` itself**:

```java
private GuiMainWindow frame;                        // Match.java:58
public void setFrame(final GuiMainWindow compoIn)   // Match.java:636
public GuiMainWindow getFrame()                     // Match.java:645
```

`GuiMainWindow extends JFrame`, and the observed chronology is consistent with resolution of those
descriptors dragging in `Component → Container → Window → Frame → JFrame` and then `GuiMainWindow`.

**Two bounds on this, both deliberate.** First, **the chronology alone does not isolate which
descriptor triggered resolution** — the field, `setFrame`'s parameter and `getFrame`'s return type
are all candidates, and the log cannot separate them. The causal story is plausible and
well-supported, not proven. Second, **this is a property of the qualified runtime, not of every
JVM**: it shows that constructing `Match` from the official JAR under **Temurin 17.0.20.1** loads
`GuiMainWindow`. Eager type resolution is implementation-specific, and another JVM might resolve
lazily.

**Within the qualified runtime the requirement is unsatisfiable**, and not by a better probe:
`FindMove.setMatch()` requires a `Match`, and constructing one loaded the GUI class here.

## Not a second failure — an incomplete bootstrap in the probe

```
Exception in thread "main" java.lang.NullPointerException:
  Cannot read field "valueY" because "<parameter1>" is null
    at net.schwagereit.t1j.Zobrist$Node.access$200
    at net.schwagereit.t1j.Zobrist.getPinValue
    at net.schwagereit.t1j.Board.setPin
    at net.schwagereit.t1j.E2Probe.main(E2Probe.java:63)
```

`Zobrist` allocates `private final Node[][] field = new Node[MAXDIM][MAXDIM]` but leaves every
entry **null** until `initialize()` populates them via `fill(i, j)`. `Match()`'s constructor calls
`boardY.setZobristEnabled(true)`, so `Board.setPin` consults the table on the very first pin — and
dereferences null.

**The probe never called the initialization the application calls.** Both routines are **public**,
on classes with **zero AWT/Swing imports**:

| routine | declaration | AWT/Swing imports |
|---|---|---|
| `Zobrist.getInstance().initialize()` | `public final void initialize()` — `Zobrist.java:56` | 0 |
| `CheckPattern.getInstance().loadPattern()` | `public final void loadPattern()` — `CheckPattern.java:373` | 0 |

`loadPattern()` reads a classpath resource (`getResourceAsStream`), not a display.

What the evidence supports is only this: **no dedicated headless bootstrap entry point was
identified.** The two routines are public and callable, but the sole call site in the codebase is
`Control.java:141`, inside `Control.main()`, three lines after `setNiceFont()`. So a driver must
invoke them itself rather than finding an engine-level `init()`.

**This is not evidence that the engine cannot initialize**, and it does not make the probe
defect-free — the omission was the probe's. **The E2 gate fails independently, on the GUI class
load, whether or not this is fixed.**

## What this means for T1j as an anchor

E1 rated headless operation `~` and called the path "narrow but plausible". E2 attempt 1 narrowed
that to "blocked on the published API". Attempt 2 adds two things:

- **Under the qualified runtime, a GUI class loads when `Match` is constructed.** The previous
  class-load criterion cannot be met by any driver of the search.
- **T1j remains potentially headless with GUI classes merely resident** — loading `GuiMainWindow`
  is not the same as creating a window, and the JVM stayed headless throughout. But establishing
  that requires **relaxing the class-load criterion** from "no GUI class loads" to "no window is
  created".

A driver would need: reflection into `Match.moveNr`, tolerance of `GuiMainWindow` and the Swing
chain being resident, and manual calls to `Zobrist.initialize()` and `CheckPattern.loadPattern()`.
That is more than "narrowly scoped private-state injection" describes, and the reviewer should
price it as such.

**Stated at the authorized width:** this run does **not** show T1j cannot be driven headlessly — it
loaded, stayed headless, left the checked host surfaces untouched, and the JVM ran its 2007
bytecode. It shows the class-load criterion is unmeetable in this runtime, and that the remaining
question — whether a move comes back — is still open because the probe's bootstrap was incomplete.

Nothing here is a strength claim, a determinism claim, or a rules-equivalence claim. One position,
one attempted call, no game, no seeds.

## Options, for the reviewer — none acted on

1. **A third attempt with the criterion re-scoped.** Tolerate GUI classes loading while requiring
   that **no window is created**, call the two public initialization routines, retain the single
   `Match.moveNr` reflection, and run one move. This is the smallest change that makes the
   remaining question answerable.
2. **Weigh the integration cost.** Three interventions — reflection, resident GUI classes, manual
   engine init — is a larger commitment than E0 priced, and the claim it would support is
   "headless execution with GUI classes resident and initialization hand-driven".
3. **Reconsider the ladder.** T1j remains uncalibrated; E3–E4 were always going to yield an
   ordering, not a placement. This raises the cost side without moving the benefit.
