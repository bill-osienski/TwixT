## The new failure

```
java.lang.IndexOutOfBoundsException: Index 5 out of bounds for length 0
  at java.util.ArrayList.get
  at net.schwagereit.t1j.Match.getMoveX
  at net.schwagereit.t1j.OrderedMoves.generateNewMoves
  at net.schwagereit.t1j.FindMove.alphaBeta          (x3 frames)
  at net.schwagereit.t1j.FindMove.internalComputeMove
  at net.schwagereit.t1j.FindMove.computeMove
  at net.schwagereit.t1j.E3Probe.run(E3Probe.java:161)
```

`OrderedMoves.generateNewMoves` reads the **last played move** from the match:

```java
int xc = match.getMoveX(match.getMoveNr());   // OrderedMoves.java:222
int yc = match.getMoveY(match.getMoveNr());   // OrderedMoves.java:223
```

`getMoveX(6)` indexes `moves.get(5)`, and `moves` is empty — hence "Index 5 out of bounds for
length 0".

**`moveNr` and `moves` are two halves of one invariant, and the authorization permitted writing
only one of them.** Setting the counter to 6 tells the search six moves have been played; the list
says none have. The search believes the counter and dereferences the list.

**Correctly classified: this is a scope limitation of the authorized injection.** It is not
evidence that T1j's search is unusable, and the probe is not defect-free — a coherent position was
never actually constructed. Populating `moves` would have been a fourth reflective access, which
was not authorized, so the probe did not attempt it.

**The search executes.** It loaded, initialized, **accepted all board pins**, entered
`computeMove()`, and reached three `alphaBeta` frames before hitting the inconsistency I injected.
The *board* accepted every pin; the *`Match`* position as a whole was incoherent, which is
precisely what the throw exposed. What has never been
obtained is a **coherent position**, because every route to one needs something the successive
authorizations did not include.

**Two routes exist, both grounded in the source, neither attempted:**

1. **Populate `moves` reflectively as well** — a fourth reflective access. Keeps everything else
   identical.
2. **Set `nextPlayer` reflectively and then call `setlastMove()` six times.** This is arguably
   cleaner: `setlastMove` populates `moves` *and* `moveNr` together through T1j's own move path, so
   the state is consistent by construction, and it needs **no** `moveNr` write. It was impossible
   before this attempt because it routes through `GuiBoard.getHoleName()`, whose **body is a pure
   formatter** (`COL_NAMES[x] + (y+1)`, `GuiBoard.java:91`) and which **does not construct a
   `GuiBoard` or a `Window` in source**. That is the accurate statement — **not** that it has "no
   display dependency": `GuiBoard` is `public final class GuiBoard extends JPanel` and its class
   initializer builds static AWT `Color` fields (`GuiBoard.java:57`), so calling the method does
   load a Swing component subclass. That is permitted now the criterion is relaxed, but it is a
   real consequence, and `GuiBoard` was **not** loaded in this attempt. `nextPlayer` is 0 after
   `new Match()` and is set only by `prepareNewMatch` (`Match.java:109`), which is why one
   reflective write is still needed.

   **Conditions recorded from review for route 2, should it ever be authorized** — not acted on
   here: set `nextPlayer` reflectively **once**; **do not pre-place pins**; submit the six moves in
   **alternating-player order** through `setlastMove()`; let T1j populate both boards, `moves`,
   `moveNr` and player state **together**; and perform the final window, preferences and reflection
   checks in a **`finally` block**, so an exception cannot skip them as it did here.
